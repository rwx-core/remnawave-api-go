# rwx-core/remnawave-api-go

Клиент API панели Remnawave, которым владеем мы: генерируется ogen из опубликованной
OpenAPI-спеки вендора. Ни одна строка кода в `api/` не написана руками и не скопирована
из чужого SDK.

## Зачем он нужен

Вендор требует пинить SDK под версию панели. Community-SDK за ней не успевает: последний
релиз — `v3.4.4`, панель уже `3.4.5`. Проверено на 2026-10-13: `go list -m -versions
github.com/Jolymmiles/remnawave-api-go/v3` отдаёт единственную `v3.4.4`.

Полная спека панели (162 пути) при этом **не генерируется в принципе**. В 3.4.x каждая
операция описывает тело ошибки как `oneOf` без дискриминатора, а ogen такие объединения
различать не умеет: он пропускает операцию целиком. На полной спеке это 218 пропущенных
операций и ноль из нужных нам. Обе версии генератора ведут себя одинаково — v1.24.0
(текущая) и v1.19.0 (та, на которой собран community-SDK); второй вообще падает на
разборе спеки.

Поэтому клиент строится из урезанной спеки: только те операции, которыми реально
пользуется rwx-store. Это 10 операций, 11 схем и 23 000 строк вместо 233 000 у полного
SDK. Три правки относительно документа вендора перечислены ниже — каждая закрыта
тестом.

Подходы мы переняли у community-SDK: у него в `.ogen.yml` включён `infer_types`, а
`scripts/smart_consolidate.py` содержит `unify_error_responses` — то есть ту же задачу с
тем же генератором они решили своим пайплайном. Отличия: мы делаем это механически, без
выдуманных полей, и оставляем тесты, которые падают, если правки отвалятся.

## Что здесь лежит

| Файл | Что это |
|---|---|
| `openapi-3.4.5.json` | полная спека вендора, как есть. Её собственность Remnawave, мы её только храним |
| `tools/trim-spec.py` | строит урезанную спеку из полной: режет лишние операции и схемы, сливает объединения, правит известные ошибки вендора |
| `openapi-trimmed.json` | результат. Это контракт, по которому сгенерирован `api/` |
| `api/` | сгенерированный клиент. Не править руками |
| `api/behaviour_test.go` | тесты, которые держат наши правки (см. ниже) |
| `ogen.json` | настройки генератора |

## Что мы поменяли относительно спеки вендора

Обе правки — в `tools/trim-spec.py`, обе зафиксированы тестами.

**1. Идентификаторы принудительно целые.** Вендор объявляет `userId` как `type: number`
без целочисленного формата. ogen рендерит `number` как фиксированную точку, и
`GET /api/users/12345` уходит как `/api/users/12345.0000000000`, который панель
отвергает. В спеке 3.4.4 был `integer` — это регрессия вендора, и `infer_types` её не
лечит (проверено: с флагом параметр всё равно остаётся float). Панель принимает целое,
поэтому здесь параметр объявлен как `integer/int64`.

**2. Объединения в теле ошибок слиты в одну схему.** Ответ `400` объявлен как
`oneOf [RemnawaveBadRequestErrorDto, RemnawaveValidationErrorDto]` — бизнес-ошибка и
ошибка валидации с разными формами под одним кодом. Объединения без дискриминатора ogen
не генерирует. Мы не вырезаем такие ответы и не выдумываем форму: сливаем объединение в
один объект, properties — объединение properties участников, `required` — пересечение
required участников, а ограничение (`enum`, `format`) остаётся **только если все
участники объявляют одно и то же**.

Последнее — не аккуратность, а необходимость. `message` у бизнес-ошибки закреплено
перечислением известных строк, у ошибки валидации — нет, и ogen проверяет enum при
декодировании. Наивное слияние превратило бы любое сообщение панели вне того списка в
ошибку декодирования, и обычный 400 перестал бы объяснять себя. Итог:
`RwxUnifiedRemnawaveBadRequestErrorDto` с единственным обязательным полем `message`,
которое принимает обе формы панели.

**3. Поля устройств снова nullable.** В спеке 3.4.4 у `platform`, `osVersion`,
`deviceModel`, `userAgent`, `requestIp` стояло `"nullable": true` и они не были в
`required`; в 3.4.5 они стали обязательными. VPN-клиент, не reporting модель и
платформу, — обычное дело, и тогда одно такое устройство роняет декодирование всего
списка. Возвращаем nullable: старая декларация вендора и есть доказательство.

Оба 400-ответа приходят типизированными, а не «сырой» ошибкой:

```go
res, err := client.UsersControllerCreateUser(ctx, body)
switch v := res.(type) {
case *api.RwxUnifiedRemnawaveBadRequestErrorDto: // 400, обе формы
case *api.RemnawaveNotFoundErrorDto:             // 404
case *api.UserResponseDto:                       // 200
}
```

Статусы, которых нет в спецификации (например, 503 от прокси), приходят как
`*validate.UnexpectedStatusCodeError` — с кодом статуса и **читаемым** `Payload.Body`.
Классифицировать такие ответы надо по коду статуса, а не по тому, декодировалось ли тело:
у типов ошибок вендора есть обязательные поля, и неполное тело превращается в ошибку
декодирования вместо «пользователь не найден».

## Работа с клиентом

Конструктор требует источник авторизации. Панель использует bearer, готового хелпера в
клиенте нет — интерфейс тривиальный:

```go
type bearerAuth struct{ key string }

func (a bearerAuth) Authorization(context.Context, api.OperationName) (api.Authorization, error) {
	return api.Authorization{Token: a.key}, nil
}

client, err := api.NewClient(panelURL, bearerAuth{key: apiKey})
```

Методы называются по `operationId` из спеки, поэтому с префиксом контроллера:
`UsersControllerCreateUser`, `InternalSquadControllerGetInternalSquads`,
`HwidUserDevicesControllerGetUserHwidDevices`.

## Версии

Тег релиза совпадает с версией панели: `v3.4.5` — значит клиент собран из спеки 3.4.5.
Модуль `/v3` в пути повторяет мажорную линейку панели, чтобы совпадать с раскладкой
community-SDK: переключение зависимости в rwx-store меняет только имя модуля.

## Регенерация

```sh
make generate   # пересобрать урезанную спеку и клиент
make check      # пересобрать и упасть, если что-то разошлось с закоммиченным
make test       # сборка, vet, тесты
```

Смена версии панели: положить новую полную спеку, поправить `SPEC_VERSION` в `Makefile`,
прогнать `make generate`. Если вендор переименует или уберёт нужную операцию,
`tools/trim-spec.py` остановится с ошибкой, а не урежет контракт молча.
